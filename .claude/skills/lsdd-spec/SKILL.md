# spec のドラフトを書く

引数: $ARGUMENTS

1つ目の語が spec のファイル名、残りが要望である。

## 手順

1. `git status` を実行する。ブランチ名と、作業ツリーが clean かどうかを報告に書く。
2. 要望に関係するコードと、その周りの既存テストを読む。読んだファイルを報告に挙げる。
3. `spec/<ファイル名>.md` を、次の節で書く。
   - **背景**: 要望をそのまま書く。推測で足さない。
   - **目的**: 1〜2文。
   - **対象範囲**・**対象外**: 今回の変更に巻き込まれそうな既存の振る舞いは、対象外に「変えない」と明記する（例: 既存の検索の結果）。
   - **受け入れ条件**: 番号を付ける。外から確かめられる形で書き、実装の手段（クラス名、データの形）は書かない。
   - **確認方法**: 受け入れ条件ごとに1本以上。自動テストで確かめるものと、人が確かめるもの（行末に「（人が確認）」）を分ける。確認を始める前の状態（何が保存されているか、など）を書く。何もしなくても通ってしまう確認にしない。
   - **未解決事項**: 要望とコードからは決まらない点。項目ごとに「暫定:」と理由を1行添える。依頼元に聞けば決まるものには「（依頼元に確認）」を付ける。
4. 倣うべき前例（既存の似た処理）があれば、spec の末尾に挙げる。前例どうしで扱いが割れていれば、割れていることを未解決事項に書く。
5. **lsdd-reviewer エージェントに spec をレビューさせる**（種類: spec、対象: 書いた spec のパス）。指摘のうち、決めることを伴わないもの（書き漏れ、番号のずれ、文書内の食い違い）は直す。決めることを伴う指摘は直さず、報告に挙げる。
6. 報告して止まる。コードは変更しない。コミットしない。

## 報告に書くこと

- 作業ツリーの状態
- 読んだファイル
- spec の要約（受け入れ条件の数、確認方法の数、未解決事項の数）
- reviewer の指摘の一覧と、直したもの・直さずに残したもの（残した理由）
- 依頼元に確認すべき未解決事項
- 実行しなかった指示（あれば、名指しで理由付き）
