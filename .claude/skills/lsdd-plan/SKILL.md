# 実装プランを書く

引数: $ARGUMENTS

1つ目の語が spec のファイル名、2つ目があればタスク番号である。プランのファイルは、タスク番号があれば `plans/<ファイル名>-task<番号>.md`、無ければ `plans/<ファイル名>.md` とする。

## 手順

1. spec・notes・tasks（あれば）を読む。tasks が無ければ、spec の確認方法を完了基準にする。
2. プランを書く前に、テストを全件1回実行し、結果（成功・失敗の件数）をプランの冒頭に記録する。
3. プランに次の節を書く。
   - **前提**: 参照した文書、着手前のテスト結果。
   - **変更対象**・**新規作成**: ファイルごとに何を変えるか。notes の「関係するファイル」と食い違うなら、理由を書く。
   - **テスト**: 完了基準の確認方法の行ごとに、どのテストで確かめるか。各テストの期待値の出どころ（入力から決まる値、仕様から決まる値、変更していない別の部品が返す値など）を書く。実装を動かして出た値を期待値にしない。
   - **確認**: 実行するコマンド。依存の登録（DI など）を変えるなら、アプリを起動して画面を開く確認を入れる。
   - **要レビュー**: 人が決める選択。項目ごとに既定案・別案・それぞれの理由を書き、「指示がなければ既定案で進める」と添える。notes の「計画で決めること」と、tasks の「計画で決めること」は必ずここに挙げる。テストのためにプロダクトコードに手を入れる案には、外から見える振る舞いが変わらないかを書く。
4. **lsdd-reviewer エージェントにプランをレビューさせる**（種類: plan、対象: プラン・spec・notes・tasks のパス）。決めることを伴わない指摘は直し、伴うものは要レビューに足すか報告に挙げる。
5. 報告して止まる。コードは変更しない（テストの実行は除く）。コミットしない。

## 報告に書くこと

- 着手前のテスト結果
- 変更対象の一覧、テストの数
- 要レビューの一覧（既定案）
- reviewer の指摘と対応
- 実行しなかった指示（あれば）
