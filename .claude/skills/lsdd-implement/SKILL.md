# プランどおりに実装する

引数: $ARGUMENTS

1つ目の語がプランのパスである。残りがあれば、人からの補足として従う。

## 手順

1. プランを読む。「要レビュー」に人の決定が書かれていなければ、実装せずに止めて、その旨を報告する。
2. バグ修正のプランで、再現テストがあるときは、修正の前に再現テストだけを追加して実行する。テストランナーの出力をそのまま報告に貼り、症状を捉えたアサーションで落ちたか（期待値と実際の値）を書く。落ちなければ、修正せずに止めて報告する。
3. プランの「変更対象」「新規作成」だけを変える。プランから外れる必要が出たら、外れた点と理由を報告に書く。
4. プランの「確認」を実行する。
   - テストは、テストランナーの出力をそのまま報告に貼る（要約だけにしない）。
   - 起動確認は行ってよい。要求ごとに、URL・状態コード・画面から取った値をそのまま報告する。判定は書かない（人が行う）。
   - spec や tasks で「（人が確認）」とした項目は行わない。
   - アプリを起動したら、終わったら止める。
5. **lsdd-reviewer エージェントに実装の差分をレビューさせる**（種類: implementation、対象: プランのパス。差分は reviewer が git で取る）。決めることを伴わない指摘（プランどおりでない箇所、テストの抜け）は直してから確認をやり直す。伴うものは報告に挙げる。
6. 報告して止まる。コミットしない。

## 報告に書くこと

- 変更したファイルの一覧（`git status --short` の出力そのまま）
- テストランナーの出力（そのまま）
- 起動確認の観測値（そのまま）
- プランから外れた点と理由
- reviewer の指摘と対応
- 実行しなかった指示（あれば）
