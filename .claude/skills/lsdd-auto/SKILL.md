# spec の承認後を通しで進める

引数: $ARGUMENTS

1つ目の語が spec のファイル名である。残りに「プランも任せる」があれば、実装プランを人のレビューに回さずに進める（停止条件 S3）。それ以外の残りは、人が決めたこと・指示として扱う（前回止まった点への答え、プランの承認など）。

## 進め方

各フェーズの中身は、このリポジトリのフェーズごとのスキルの手順に従う。`.claude/skills/<スキル名>/SKILL.md` を読み、その「手順」を実行する。そのとき、次のように読み替える。

- 各スキルの「報告して止まる」は、「下の停止条件を確かめ、当たらなければ次のフェーズへ進む」と読み替える。
- 各スキルの「引数」は、このスキルが決めた値（spec のファイル名、プランのパスなど）に読み替える。
- 「人が決める」「人の決定」とある箇所は、下の停止条件で人に返すものを除き、このスキルが決めて、決めたことと理由を報告に書く（tasks を作るかどうか、など）。
- reviewer にレビューさせる手順は省かない。

フェーズは次の順に進める。すでに済んでいるフェーズは飛ばし、どこから始めたかを報告に書く。

0. **準備**: `git status` を実行する。`node .claude/hooks/guard.test.mjs` を実行し、ガードの自己検査の結果を報告に書く。
1. **spec**: 未解決事項を確かめる（S1）。spec が未コミットなら、spec だけをコミットする（lsdd-docs-commit の手順）。
2. **探索**: lsdd-explore。
3. **tasks**: lsdd-tasks。作るかどうかは、そのスキルの「判断材料の示し方」に沿って決める。作った場合は、次の 4〜7 をタスクの順に繰り返す。
4. **実装プラン**: lsdd-plan。
5. **文書のコミット**: lsdd-docs-commit（notes・tasks・plans）。
6. **実装と自動の確認**: lsdd-implement。
7. **閉じるか止まるか**: そのプラン（またはタスク）に人が確かめる項目が残っていれば S8 で止まる。残っていなければ、lsdd-close の手順で閉じ（「人が確かめた結果」は「人が確かめる項目は無い」とする）、次のタスクへ進む。

済んだかどうかは、成果物と人の答えで決める。

- notes・tasks があれば、探索・tasks は済んでいる。
- プランは、要レビューのすべての項目に「決定:」か「決定（自走）:」があれば済んでいる。人がこのスキルの引数でプランを承認した、または要レビューに答えたときは、まずその答えをプランの要レビューに「決定:」として書いてから進む。
- 文書のコミットは、`git status` で spec・notes・tasks・plans に未コミットの変更が無ければ済んでいる。

## 停止条件

当たったら、その場で止まる。推測で進まない。報告の先頭に「停止: S<番号>」と理由を書き、作りかけの成果物は保存して、どこまで済んだかを書く。

| 番号 | 条件 | 人に返すもの |
|---|---|---|
| S0 | ガードの自己検査が落ちる | 落ちた項目 |
| S1 | spec の未解決事項に、「（依頼元に確認）」が付いたまま「決定:」の無いものがある | 確認すべき項目 |
| S2 | notes の「spec に戻すべき点」が空でない（探索の結果が、受け入れ条件・対象範囲と食い違う） | 戻すべき点と、spec をどう直すかの案 |
| S3 | 「プランも任せる」が無いとき: 実装プランを書き終えた（人がプランをレビューする）。「プランも任せる」があるとき: 要レビューのうち、外から見える振る舞いか spec の範囲を変えるものが残った。実装の手段の選択は、既定案に「決定（自走）:」と理由を書いて進む | プランの要約と、要レビューの一覧 |
| S4 | 同じテストが、直しても3回続けて落ちる | 落ちたテストの出力と、戻り先（プラン・tasks・spec）の案 |
| S5 | 外の要因で進めない（ツールが無い、権限が拒否された、ガードに止められた） | 何が足りないか |
| S6 | プランの変更対象・新規作成の外に、変更が要る | 外れる点と理由 |
| S7 | 再現テストが、修正の前に落ちない（バグ修正のとき） | テストとテストランナーの出力 |
| S8 | 自動の確認がすべて終わり、人が確かめる項目が残っている。サイクル（またはタスク）の最後は、ふつうここで止まる | 人が確かめる項目の一覧と確かめ方（アプリの起動方法、URL、見る値）、閉じるときに呼ぶ `/lsdd-close` の引数の形 |
| S9 | reviewer が同じ指摘を2回続けて出す、または同じ誤りを2回繰り返した | 繰り返した内容 |
| S10 | reviewer の指摘のうち「決めることを伴う」もので、外から見える振る舞いか spec の範囲に関わるもの | 指摘と選択肢 |

権限の拒否やガードの停止は、別の手段で回避しない。その操作が要るなら S5 で止まる。

## 再開

人が答えを添えてもう一度呼んだら、答えを該当の文書に反映してから（spec なら未解決事項に「決定:」、プランなら要レビューに「決定:」）、止まったフェーズから続ける。spec を直した場合は、spec を直したことで変わる後のフェーズ（notes の前提、プラン）も見直す。

## コミット

- 文書のコミットは、フェーズ1・5 で作る。実装のコミットは、フェーズ7 で閉じるときだけ作る（人が確かめる項目が残るときは、人が確かめた後に `/lsdd-close` で作る）。
- 既存のコミットは書き換えない。

## 報告に書くこと

- 停止: S<番号> と理由（先頭）
- どのフェーズから始め、どこまで済んだか
- フェーズごとの成果物と要約（reviewer の指摘の数、直したもの・残したもの）
- このスキルが決めたこと（tasks を作るかどうか、「決定（自走）:」とした要レビュー）と理由
- 人に決めてほしいこと（番号付き）
- 実行しなかった指示（あれば）
