# 探索して notes に書く

引数: $ARGUMENTS

1つ目の語が spec のファイル名である。残りがあれば、人が特に見てほしい点として扱う。

## 手順

1. `spec/<ファイル名>.md` を読む。
2. 関係するコードとテストを読む。必要なら、リポジトリのファイルを変えない範囲でアプリを動かして確かめてよい（動かしたら必ず止める）。
3. `notes/<ファイル名>-investigation.md` に、次の節で書く。
   - **関係するファイル**: ファイルごとに、今回の変更とどう関係するか。
   - **データの流れ**: 要求から画面に出るまで、今回の変更が通る経路。
   - **似た実装**: 倣えるもの。無ければ「無い」と書き、どこまで探したかを添える。
   - **受け入れ条件の前提**: 受け入れ条件ごとに、前提となる既存コードの事実と、その根拠（ファイル:行）。見つからなければ「見つからない」と書く。
   - **動かして確かめたこと**: コードを読んで判断したことと分けて書く。
   - **計画で決めること**: コードからは決まらず、実装プランで選ぶ必要がある点。
   - **spec に戻すべき点**: spec の前提と食い違う事実、spec で決めておかないと受け入れ条件が判定できない点。
4. **lsdd-reviewer エージェントに notes をレビューさせる**（種類: notes、対象: notes のパスと spec のパス）。決めることを伴わない指摘は直し、伴うものは報告に挙げる。
5. 報告して止まる。コードと spec は変更しない。コミットしない。

## 報告に書くこと

- notes の要約（関係するファイルの数、計画で決めることの数）
- spec に戻すべき点（あれば）
- reviewer の指摘と、直したもの・残したもの
- 実行しなかった指示（あれば）
