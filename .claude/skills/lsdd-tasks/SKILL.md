# tasks を作るかを示し、作るならドラフトを書く

引数: $ARGUMENTS

1つ目の語が spec のファイル名である。2つ目に「作る」「作らない」があれば、人の決定として従う。無ければ、判断材料を示してから、作るべきと考える場合だけドラフトを書く。

## 判断材料の示し方

spec の確認方法をすべて実装の最後にまとめて実行したとして、落ちた確認から、原因になった変更の場所を絞れるかを考える。

- 絞れるなら、tasks は作らない案を示す。spec の確認方法がそのまま完了基準になる。
- 絞れない組み合わせ（例: 自動テストが通るのに画面で落ちたとき、ロジック・要求・画面のどれが原因か分からない）があれば、その境目でタスクを分ける案を示す。

作業量や受け入れ条件の数は、判断の材料にしない。

## ドラフトの書き方（作る場合）

`tasks/<ファイル名>.md` に書く。

- **共通の前提**: spec・notes の参照、テストの実行コマンド。
- **タスクごと**: 目的、変更する範囲、確認方法（spec の確認方法を番号で割り当てる。人が確かめるものは「（人が確認）」）、前のタスクへの依存。確認方法はクラス名やメソッド名に依存しない形で書く。
- **計画で決めること**: notes の「計画で決めること」を、どのタスクの実装プランで決めるか割り当てる（tasks では決めない）。
- **見送り**: 今回やらないと決めたことと、その理由。

spec の確認方法が、どのタスクにも割り当てられていない状態を残さない。

## 手順

1. spec と notes を読む。
2. 判断材料を示す。作る場合はドラフトを書く。
3. ドラフトを書いた場合は、**lsdd-reviewer エージェントに tasks をレビューさせる**（種類: tasks、対象: tasks・spec・notes のパス）。決めることを伴わない指摘は直し、伴うものは報告に挙げる。
4. 報告して止まる。コードと spec・notes は変更しない。コミットしない。

## 報告に書くこと

- 作るか作らないかの案と、その理由（原因を絞れるかの説明）
- 作った場合: タスクの一覧、確認方法の割り当て、reviewer の指摘と対応
- 実行しなかった指示（あれば）
