# Light SDD のスキル一式

Claude Code で Light SDD のサイクル（仕様 → 計画 → 実装 → 検証）を回すときに、フェーズごとのプロンプトをスキルにまとめ、各フェーズの成果物を reviewer エージェントに一度見させてから人に返すための一式。

手順と観点は、技術同人誌『Claude Code × Light SDD 実践ガイド』（[Amazon](https://www.amazon.co.jp/dp/B0HJW4VN15)）の第3章〜第5章と付録 D に沿っている。ここに書いたのは、その手順をスキルとして動かすための指示であって、手順そのものの説明ではない。

本書に無い観点を1つ追加してある。reviewer の spec の観点の「新しく読み込む値が無効・欠けている・古いときの振る舞いが書かれているか」で、試した走行で spec のドラフトがこの論点を拾わず、決めないまま実装に進んだことから追加した。

## 入っているもの

| 種類 | 名前 | 呼ぶ時点 | 人が次に行うこと |
|---|---|---|---|
| スキル | `/lsdd-spec <名前> <要望>` | サイクルの最初 | spec を読み、未解決事項を決める（依頼元に確認するものは確認する）。直す点があれば `/lsdd-revise` |
| スキル | `/lsdd-revise <文書のパス> <直す点>` | 文書を承認しなかったとき | 直った文書をもう一度読む |
| スキル | `/lsdd-docs-commit <1行>` | 文書を承認したとき | コミットの範囲を確かめる |
| スキル | `/lsdd-explore <名前>` | spec を承認した後 | notes を読み、spec に戻すべき点があれば spec を直す |
| スキル | `/lsdd-tasks <名前> [作る\|作らない]` | 探索の後 | tasks を作るかを決め、作るならドラフトを読む |
| スキル | `/lsdd-plan <名前> [タスク番号]` | 計画の最後 | プランを読み、要レビューに答える（`/lsdd-revise` でプランに決定を書かせる） |
| スキル | `/lsdd-implement <プランのパス>` | プランを承認し、文書だけのコミットを作った後 | テストの出力と差分を読み、人が確かめる項目を行う |
| スキル | `/lsdd-close <プランのパス> <人が確かめた結果>` | 人が確かめる項目をすべて終えた後 | コミットと、作業ツリーが clean になったことを確かめる |
| スキル | `/lsdd-auto <名前> [プランも任せる] [決めたこと]` | spec を承認した後（上の探索〜実装を通しで進める） | 止まった理由（停止条件 S0〜S10）を読み、決めたことを添えてもう一度呼ぶ。最後は人が確かめる項目を行い、`/lsdd-close` |
| エージェント | `lsdd-reviewer` | 各スキルの中から呼ばれる | （人は直接呼ばない） |
| 設定 | `.claude/settings.json` の許可の一覧 | 常に効く | 一覧に無い操作だけ承認を求められる |
| フック | `.claude/hooks/guard.mjs` | ファイルの書き込みとコマンドの実行の前 | 止められた操作が本当に要るかを決める |

## 人に残ること

- 要望と、依頼元に確認すること
- 各フェーズの成果物を承認するか、直させるか（reviewer の指摘のうち「決めることを伴う」ものの判断を含む）
- 要レビューへの答え
- 人が確かめる項目（画面の目視など）と、その合否
- `/lsdd-auto` を使うときは、spec の承認、止まった地点での判断、実装プランのレビュー（「プランも任せる」を付けたときは、外から見える振る舞いや spec の範囲を変える選択だけ）、人が確かめる項目

## ガードが止めるもの

許可の一覧（`permissions.allow`）は、Light SDD のサイクルで使う操作（リポジトリの中のファイルの編集、`git` の参照・`add`・`commit`、`dotnet` の `build`・`test`・`run`、`localhost` への `curl`）を承認なしで通す。一覧に無い操作は、これまでどおり承認を求められる。

`guard.mjs` は、サイクルで要らない操作を、承認の画面を出さずに止める。止めるのは次の操作である。

- `git push`、履歴の書き換え（`--amend`・`rebase`）、未コミットの変更を消す操作（`reset --hard`・`clean`・`checkout --`・`restore`）、ディレクトリごとの削除
- リポジトリの外と、`.claude/`・`.git/` の下への書き込み。ファイルの編集のツール（Write・Edit など）は、パスで判定する。Bash と PowerShell のコマンドは、リダイレクト（`>`）、出力先のオプション（`-o`・`-OutFile` など）、ファイルを書くコマンド（`cp`・`mkdir`・`tee`・`Set-Content` など）に渡したパスで判定する。`cd` でリポジトリの外に出た後は、読み取りのコマンドだけを通す。リダイレクトと出力先のオプションの書き込み先が、変数やコマンド置換で組み立てられていて判定できないときも止める
- パッケージやツールのグローバルなインストール（`npm install -g`・`dotnet tool install --global`）

一部は `permissions.deny` にも書いてあるが、`deny` はコマンドの先頭で照合するので、`bash -c "git push"` のような形はフックで止める。

ガードは、うっかり実行した操作を止めるためのもので、隔離（サンドボックス）ではない。次のものは判定しない。

- スクリプトの中での書き込み（`node -e`・`python -c`、スクリプトのファイル、ヒアドキュメントで渡したスクリプト）
- リポジトリの外の読み取り
- ツールが自分のキャッシュに書くもの（`dotnet restore` が NuGet のキャッシュに書くなど）

OS のレベルで隔離したいときは、Claude Code のサンドボックス（`/sandbox`）を使う。サンドボックスは macOS・Linux・WSL2 で動き、ネイティブの Windows では動かない（2026-10 時点の公式ドキュメント）。

フックは、動いていなくても何も表示されない。`node .claude/hooks/guard.test.mjs` で、止めるべきものを止めるか、`settings.json` に登録されているかを確かめる。`/lsdd-auto` は最初にこれを実行する。フック自身がエラーで落ちたときは、操作を通さずに止める（判定できないものを通さない）。止めた記録は `.git/lsdd-guard.log` に残る。

## 使う前に

- テストの実行コマンドを `CLAUDE.md` に書いておく（`/init` で作った初期案でよい）。
- フックの実行に Node.js を使う。
- 許可の一覧は .NET（`dotnet`）のプロジェクトを前提にしている。ほかの言語では、ビルドとテストのコマンドを差し替える。
- スキルとエージェントの定義には、モデルと effort を書いていない。セッションの設定がそのまま使われる。

## 入れ方

1. このリポジトリの `.claude/` を、自分のリポジトリの直下に写す。写す先に `.claude/settings.json` が既にあるときは、上書きせずに、このリポジトリの `settings.json` の `permissions` と `hooks` を既存のファイルに書き足す。
2. 自分のリポジトリで `node .claude/hooks/guard.test.mjs` を実行し、最後の行に `all passed` と出ることを確かめる。
3. Claude Code を、`.claude/` を置いたフォルダ（自分のリポジトリの直下）で、対話モードで起動する。フォルダを信頼するかを聞かれたら、信頼する（次の節）。
4. `/lsdd-spec <名前> <要望>` から始める。

## フォルダを信頼するまで、許可の一覧は効かない

`.claude/settings.json` の許可の一覧（`permissions.allow`）は、Claude Code でそのフォルダを信頼するまで効かない。信頼していないフォルダでは、一覧に入れた操作にも承認を求められる。同じファイルの `deny` とフックは、信頼する前から効く。Claude Code 2.1.296 の `claude -p` で、信頼していないフォルダと信頼したフォルダを比べて確かめた。

対話モードでは、フォルダを最初に開いたときに信頼するかを聞かれるので、そこで信頼する。`claude -p` で使うときも、先に一度対話モードで開いて信頼しておく。チームで使うときは、各自がそれぞれの端末で信頼するまで、許可の一覧は効かない。
